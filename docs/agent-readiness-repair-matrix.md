## Wrangler Functions placement evidence

The CI workflow runs its deploy command from the repository workspace root and passes `site` as the static asset directory. Wrangler `4 pages deploy --help` describes that positional argument as “The directory of static files to upload.” Cloudflare's Direct Upload documentation says: “When deploying a project using Wrangler, if a `functions` folder exists where the command is run, that `functions` folder will be uploaded with the project.” Cloudflare's Functions guide further says: “Make sure that the `/functions` directory is at the root of your Pages project (and not in the static root, such as `/dist`).” Thus repository-root `functions/` is the supported location for this CI command; `site/functions/` would put it inside the static root, contrary to the documented layout. The Functions stay in repository-root `functions/`; no workflow path change is needed.

Local Wrangler 4.148.0 confirmation: `npx wrangler@4 pages functions build functions --project-directory . --build-output-directory site --outdir node_modules/.cache/lumafare-functions` returned `Compiled Worker successfully`. The deploy help's static directory argument and Functions directory are separate inputs. The MCP and A2A handlers use only JavaScript runtime APIs and the existing local article asset; `package.json` has no dependencies, so CI does not need an `npm ci` workflow step.

Official sources: [Wrangler Pages deploy help](https://developers.cloudflare.com/workers/wrangler/commands/pages/), [Pages Direct Upload: Functions](https://developers.cloudflare.com/pages/get-started/direct-upload/), and [Pages Functions: Get started](https://developers.cloudflare.com/pages/functions/get-started/).

## DNS-AID preflight evidence

On 2026-10-08, Cloudflare DoH returned `AD=true` for the public DS and DNSKEY queries for `lumafare.com`; the queried DS was key tag 2371, algorithm 13, digest type 2. The same validating resolver returned no SVCB answer for `_index._agents.lumafare.com` (type 64). The saved Cloudflare legacy API credential returned HTTP 403 / error 9103, so account ownership and DNS-edit permissions could not be verified; no DNS record was changed.

The current IETF DNS-AID draft is `draft-mozleywilliams-dnsop-dnsaid-02`, last updated 2026-05-27. It specifies an SVCB query for `_index._agents.<domain>` and requires using a non-underscored TargetName, while stating that the organization index data, protocols, and schemas are out of scope. It does not define the historical private SvcParamKey `key65409`; therefore that parameter was not published and DNS-AID remains unconfigured pending an interoperable index-location convention and verified DNS-edit access. [IETF Datatracker draft](https://datatracker.ietf.org/doc/draft-mozleywilliams-dnsop-dnsaid/)
